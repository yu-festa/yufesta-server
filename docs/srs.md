## 1. 개요

### 1.1 목적
본 문서는 「YU FESTA」의 기능·비기능 요구사항을 정의하여 설계(ERD·API·와이어프레임)와 구현, 검수의 기준으로 삼는다.

### 1.2 범위
축제 방문객이 설치 없이 QR로 접속하는 모바일 웹 서비스. **읽기는 로그인 없이, 쓰기(신청·작성·신고)는 소셜 로그인(카카오·구글) 후 자동 생성 닉네임으로 익명 표시**를 원칙으로 한다. 예외로 **응원 메시지 작성은 로그인 없이** 가능하다(2차 회의 결정, 8장).

| 기능 | 요약 | 로그인 |
|---|---|---|
| 인스타팅 | 2회차 일괄 매칭. 발표 시각에 상대 인스타 ID 즉시 공개. 홈에 카운트다운 블록 | 신청·결과 |
| 타임테이블 | 공연 일정, 진행 중 표시, 순서 변경 실시간 반영 | 불필요 |
| 라인업(동아리 홍보) | 공연 동아리 소개 카드·캐러셀 | 불필요 |
| 축제 지도 | 카카오맵 핀, 카테고리별 보기, 내 위치, 가까운 화장실 안내, 폴백 지도 | 불필요 |
| 축제 사진 | 운영진·관계자가 올리는 무대·부스·현장 사진 | 읽기 불필요 (업로드는 운영자) |
| 공지 | 운영자 공지 | 읽기 불필요 |
| 분실물 | 습득·분실 게시. 자동 생성 닉네임으로 표시. 콘텐츠 필터 적용 | 읽기 불필요 / 작성 필요 |
| 응원 메시지 | 메시지 티커. 자동 생성 닉네임으로 표시. 콘텐츠 필터 적용 | 읽기·작성 모두 불필요 (신고는 필요) |
| 운영자 화면 | 회차 발표, 콘텐츠·신고 관리 | 운영자 |

**범위 제외**: 사용자 사진 업로드(UGC) — 1차 회의에서 제거 결정, 운영진 게시형 축제 사진(3.10)으로 대체. 동성 매칭 옵션 — 보류(8장). 게스트 계정 모델 — 철회(8장). 화장실 비치 용품 정보 — 제외(8장). 채팅, 결제, 네이티브 앱, 학교 인증, 외부 인증 서비스(Firebase 등).

### 1.3 용어
| 용어 | 정의 |
|---|---|
| 회원 | 카카오 또는 구글 로그인을 마친 사용자. 응원 메시지 작성을 제외한 모든 쓰기 행위의 주체 |
| 익명 표시 | 화면·API 응답에는 서버가 자동 생성한 닉네임만 노출하고 작성자 식별 정보(uid, 익명 키)는 노출하지 않는 것. 분실물은 uid를, 응원 메시지는 익명 키만 서버에 기록한다 |
| 자동 생성 닉네임 | 게시물 저장 시 서버가 만들어 붙이는 표시명(예: "수줍은 펭귄"). 사용자가 정하거나 바꿀 수 없고, 게시물마다 새로 생성되어 글 간 연결이 불가능하다 |
| 회차 | 신청 마감 → 일괄 매칭 → 발표로 이어지는 단위. 당일 2회 |
| 발표 시각 (T) | 결과를 모든 신청자에게 동시에 공개하는 시각. 마감은 T − 10분 |
| 다수 측 / 소수 측 | 회차 내 성별 풀 중 인원이 많은 쪽 / 적은 쪽 |
| 1:N 매칭 | 성비 불균형 시 소수 측 1인에게 다수 측 최대 N인이 자동 배정되는 것 |
| 로그인 게이트 | 쓰기 행위 시도 시 소셜 로그인을 요구하는 지점 |
| 익명 키 | 비로그인 작성(응원 메시지)의 속도 제한과 운영자 일괄 숨김을 위해 서버가 브라우저에 발급하는 무작위 쿠키 값. 회원 계정과 연결하지 않으며 서버에는 해시만 저장한다 |
| 콘텐츠 필터 | 응원 메시지·분실물 본문에 저장 전 적용하는 3단계 검사(정규식 → 금칙어 → LLM 모더레이션 API). 3.11 |
| 폴백 지도 | 카카오맵 로드 실패 시 대체되는 캠퍼스 일러스트 지도 |
| SSE | Server-Sent Events. 서버→클라이언트 단방향 실시간 갱신 |

## 2. 전체 설명

### 2.1 제품 관점
독립형 웹 서비스. 외부 시스템은 카카오·구글 로그인(OAuth 2.0), 카카오맵 JavaScript SDK, 브라우저 Geolocation API, 텍스트 모더레이션 API(OpenAI Moderation, 3.11)에 의존한다. 인증·백엔드·DB·실시간 서버는 AWS에 **자체 구축**한다(외부 인증 서비스 미사용).

### 2.2 사용자 특성
| 사용자 | 특성 | 접근 |
|---|---|---|
| 재학생 | 주 참여층. 모바일 사용 능숙 | 전체 |
| 외부 방문객 | 타 학교·지역 주민. 재학생 커뮤니티 접근 불가 | 전체 |
| 운영자 | 총동아리연합회·제안팀. 당일 현장 상주 | 운영자 화면 |

### 2.3 운영 환경
- 클라이언트: 모바일 브라우저(iOS Safari 16+, Android Chrome 최신 2버전, 카카오톡 인앱 브라우저), 데스크톱은 중앙 정렬 보조 지원
- 서버: AWS (상세 7장)
- 운영 기간: 축제 전후 약 1주. 축제 당일 2026-10-08

### 2.4 설계·구현 제약
- **읽기 기능은 로그인 없이**, 쓰기 기능(인스타팅 신청·결과, 분실물 작성, 신고)은 소셜 로그인(카카오·구글) 후 이용. 로그인은 쓰기 시도 시점에만 요구한다. 응원 메시지 작성은 로그인 없이 익명 키·콘텐츠 필터·속도 제한으로 관리한다
- 학교 인증·학번·실명·전화번호 미수집 (제안서 약속)
- 개인정보는 축제 종료 후 7일 내 파기
- 프론트와 API는 같은 등록 도메인에 두어 인증 쿠키를 공유한다
- 카카오 콘솔(지도 SDK 도메인, 로그인 Redirect URI)과 Google Cloud 콘솔(OAuth 클라이언트, Redirect URI)에 최종 도메인 등록 필요

### 2.5 가정 및 의존성
- 전체 이용자 약 500명 예상. 설계 여유로 회차별 신청자 최대 500명, 발표 순간 동시 접속 최대 1,000명, 회원 최대 3,000명으로 가정
- 1회차 접수는 서비스 사전 오픈(홍보 시작) 시점부터 축제 당일 마감까지 여러 날 열린다
- 공연 순서·시간 변경 정보는 총동연이 운영팀에 실시간 공유한다 `[협의]`
- 동아리 소개 자료(소개문·사진·인스타)는 총동연 경유로 수집한다
- 화장실 등 편의시설 좌표와 세부 위치(건물·층)는 팀이 사전 현장 조사로 수집한다

## 3. 기능 요구사항

### 3.1 계정·인증 (FR-AUTH)

**원칙: 읽기 비로그인 · 쓰기 로그인(응원 메시지 작성 제외) · 표시 익명 (자체 구현)**

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-AUTH-01 | 로그인 없이 이용 가능한 기능: 홈, 타임테이블, 라인업, 지도(내 위치 포함), 축제 사진, 공지 읽기, 분실물 읽기, 응원 메시지 읽기·작성, 약관 열람 | M |
| FR-AUTH-02 | 소셜 로그인(카카오 또는 구글)이 필요한 기능: 인스타팅 신청·상태·결과, 분실물 작성·삭제·해결, 신고(매칭 상대·콘텐츠). 회원 가입 절차 없이 소셜 로그인만으로 회원이 된다 | M |
| FR-AUTH-03 | 카카오·구글 로그인 모두 OAuth 2.0 인가 코드 방식으로 **서버에서** 토큰을 교환하며, 동의 항목은 계정 식별자만 요청한다(닉네임·프로필·이메일 미요청). `state` 값을 검증한다 | M |
| FR-AUTH-04 | 미로그인 상태로 쓰기 행위를 시도하면(작성 버튼·신청 버튼 등) 로그인 게이트로 이동하고, 로그인 후 원래 화면으로 복귀한다. 작성 중이던 입력값은 복귀 시 복원한다 | M / 복원 S |
| FR-AUTH-05 | 로그인 게이트는 카카오·구글 버튼을 나란히 제공하고, "왜 로그인이 필요한지"(공개 공간 책임성, 소셜 계정 정보는 식별자만)와 "화면에는 자동 생성 닉네임으로 익명 표시됨"을 안내한다 | S |
| FR-AUTH-06 | 인증 상태는 서버가 서명한 **JWT(무상태 액세스 토큰)** 로 유지한다. 페이로드는 uid·발급·만료 시각만 담고 개인정보는 넣지 않는다. 만료는 축제 종료 + 7일 | M |
| FR-AUTH-07 | 토큰은 **HttpOnly·Secure·SameSite=Lax 쿠키**로만 전달한다(SameSite=Strict는 카카오·구글에서 돌아오는 요청에 쿠키가 빠지므로 사용하지 않음). localStorage·Authorization 헤더 방식은 사용하지 않는다(SSE 인증·XSS 대응) | M |
| FR-AUTH-08 | 서버 측 토큰 폐기 목록은 두지 않는다. 차단·작성 금지 여부는 신청·배치·작성 시점에 DB로 확인한다. 강제 로그아웃이 필요해지면 Redis 거부 목록을 추가한다 | S |
| FR-AUTH-09 | 로그아웃은 쿠키 삭제로 처리한다. 신청·작성 데이터는 유지된다 | S |
| FR-AUTH-10 | 미로그인 요청에 대해 읽기 API와 응원 메시지 작성 API는 정상 응답하고, 그 외 쓰기 API는 401을 반환하여 클라이언트가 로그인 게이트로 유도한다 | M |
| FR-AUTH-11 | 카카오톡 인앱 브라우저·iOS Safari·Android Chrome에서 카카오·구글 로그인 콜백 후 쿠키가 유지되는지 실기기로 검증한다(첫 스프린트) | M |
| FR-AUTH-12 | 구글 로그인을 카카오와 동일한 흐름·화면으로 제공한다. 카카오 계정과 구글 계정은 서로 연동하지 않으며 각각 별도 회원으로 취급한다(같은 인스타 ID는 회차 내 1건만 신청 가능하므로 이중 신청은 FR-MT-13으로 방지) | M |

### 3.2 인스타팅 (FR-MT)

**회차 운영**

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-MT-01 | 매칭은 당일 **2회차**로 운영한다. **1회차는 서비스 사전 오픈(홍보 시작) 시점부터 접수해 당일 16:00에 발표**하고, **2회차는 1회차 발표 직후부터 접수해 20:00에 발표**한다. 시각은 총동연 타임테이블 확인 후 조정할 수 있으며 회차 시각은 운영자가 수정하는 설정값이다 | M |
| FR-MT-02 | 각 회차의 신청 마감은 발표 시각 10분 전이다(1회차 15:50, 2회차 19:50). 마감 이후에는 신청·수정·취소가 불가하며 서버가 배치 매칭을 실행하고 운영자가 확인한다. **다음 회차 접수는 이전 회차 발표 시점에 시작**하며, 마감~발표 사이에는 "16:00 발표 직후 2회차 접수 시작" 안내를 표시한다. 열려 있는 회차는 항상 하나다 | M |
| FR-MT-03 | 1회차 참여자는 2회차에도 참여할 수 있다. **1회차 미매칭자는 1회차 발표 시점에 1회차 신청 내용을 복사한 2회차 신청이 자동 생성**되어 포함되며(해제 = 2회차 신청 취소), 1회차 매칭자는 **결과 화면에서 "2회차도 참여"를 선택**하면 같은 방식으로 2회차 신청이 생성된다. 생성된 2회차 신청은 일반 신청과 동일하게 2회차 마감 전까지 수정·취소할 수 있다 | M |
| FR-MT-04 | 발표 시각 전에는 결과가 저장되어 있어도 사용자에게 노출하지 않으며, 발표 시각에 모든 신청자에게 동시에 공개한다 | M |
| FR-MT-05 | **"보고 싶은 공연"은 해당 회차 발표 시각 이후에 시작하는 공연만 선택할 수 있다.** 2회차 신청 화면에는 20:00 이전에 시작하는 공연을 표시하지 않고 서버도 거부한다. 2회차 신청이 자동 생성·복사될 때 조건에 맞지 않는 공연은 비우고 재선택을 안내한다. 타임테이블 변경으로 조건이 깨진 경우 배치에서 해당 공연을 점수 계산에 쓰지 않는다 | M |

**신청**

## 4. 외부 인터페이스 요구사항

### 4.1 사용자 인터페이스
- 모바일 우선, 기준 폭 390px, 가로 스크롤 없음. 하단 탭바 4개(홈 / 타임테이블 / 지도 / 라인업 — 라인업 탭은 제안)
- 모든 데이터 화면은 로딩(스켈레톤)·정상·빈 상태·오류 상태를 정의한다
- 쓰기 버튼(작성·신청·신고)은 미로그인 상태에서도 노출하되, 탭 시 로그인 게이트로 안내한다
- 지도 카테고리 선택은 한 번에 하나만 활성화되는 단일 선택으로 한다
- 디자인 시스템은 와이어프레임 단계에서 신규 정의(프로토타입 디자인은 참고용)

### 4.2 외부 서비스 인터페이스
| 인터페이스 | 용도 | 비고 |
|---|---|---|
| 카카오 로그인 (OAuth 2.0 인가 코드) | 회원 식별자 획득 | 서버 측 토큰 교환, 카카오 콘솔 Redirect URI 등록, state 검증, 동의 항목 최소화 |
| 구글 로그인 (OAuth 2.0 인가 코드) | 회원 식별자 획득 | 서버 측 토큰 교환, Google Cloud OAuth 클라이언트·Redirect URI 등록, `sub`만 사용 |
| 카카오맵 JavaScript SDK | 지도 렌더·핀 | 도메인 등록, 무료 쿼터 내 운영, 실패 시 폴백 |
| 브라우저 Geolocation API | 내 위치, 화장실 거리 | HTTPS 필수, 사용자 권한 |
| OpenAI Moderation API | 응원 메시지·분실물 텍스트 필터(3.11) | 무료 엔드포인트(요금 정책 변경 시 재확인), 서버에서 호출, API 키는 Secrets Manager, 타임아웃 2초, 실패 시 fail-open |
| 캘린더(.ics 파일) | 공연 알림 대안 (보류) | 서버 생성 파일 다운로드 |

### 4.3 통신 인터페이스
- 모든 통신 HTTPS. REST API(JSON) + SSE(`text/event-stream`) 스트림
- SSE 이벤트: 신청자 수, 회차 마감, 발표, 타임테이블 변경, 응원 메시지 신규, 공지 신규. 공개 이벤트는 비로그인 연결에도 전달되고, 발표 이벤트는 로그인 연결에만 전달된다(적용 범위 축소는 8.2 미결)
- SSE keepalive 25초, 클라이언트 자동 재연결 및 누락 이벤트 재전송(`Last-Event-ID`)
- 홈 인스타팅 블록은 `GET /match/summary` 1회 호출로 구성한다(현재·다음 회차 시각, serverNow, 신청자 수, 로그인 시 내 상태)
- 인증 토큰(JWT)은 쿠키로 전달되므로 REST와 SSE(EventSource)가 같은 방식으로 인증된다. 프론트와 API는 같은 등록 도메인(예: `festa.example.com` / `api.festa.example.com`)에 두어 쿠키를 공유한다

| Cheer | id, text, displayName, writerKeyHash?, moderationStatus(passed/skipped), reportCount, hidden, createdAt | 응원 메시지. 비로그인 작성. authorUserId 없음, 익명 키 해시만 보관 |
| ContentReport | id, targetType(cheer/lostItem), targetId, reporterUserId, reason, createdAt, reviewedAt? | 콘텐츠 신고. (targetType, targetId, reporterUserId) 유니크 |
| AdminUser | (별도 엔티티 없음) User.role(user/staff/owner)로 통합 | 운영자도 소셜 로그인 + 화이트리스트(AppSetting)로 인증. ID/PW 방식 확정 시 분리(ERD v1.0 참고) |
| AppSetting | key, value | 매칭 가중치, N, 신고 누적 기준, 닉네임 단어 목록, 금칙어 목록, 필터 임계값·활성화, 속도 제한 값 등 설정. 회차 시각은 MatchRound 행에서 관리 |

### 6.2 관계
- User 1 — N Application (회차마다 1건)
- User 1 — N LostItem, ContentReport (authorUserId / reporterUserId). Cheer는 User와 관계가 없다(익명 키)
- User 1 — N Block(reporter), User 1 — N Block(target)
- MatchRound 1 — N Application, MatchRound 1 — N Match
- Application 1 — N Application (sourceApplicationId: 2회차 자동 생성·재참여 신청의 원본)
- Application 1 — N Match (자신의 상대 목록), Match N — 1 Application(partner)
- Club 1 — N TimetableSlot, Place(stage) 1 — N TimetableSlot
- Place 1 — N FestivalPhoto, Club 1 — N FestivalPhoto, AdminUser 1 — N FestivalPhoto
- 위치 정보는 저장하지 않는다

### 6.3 익명 표시 규칙
- Cheer·LostItem의 공개 조회 응답에는 `displayName`(자동 생성 닉네임)과 요청자가 작성자인지 여부(`isMine`)만 포함하고, `authorUserId`·익명 키는 포함하지 않는다. `isMine`은 LostItem은 uid, Cheer는 익명 키 일치로 계산한다
- `displayName`은 저장 시 1회 생성해 게시물에 고정하며, uid·시각 등에서 유도하지 않는다
- 운영자 API에서만 작성자 uid와 신고 이력을 조회한다

### 6.4 파기 정책 반영
- User, Application, Match, Block(개인 식별 가능 부분), ContentReport의 reporterUserId, LostItem의 authorUserId, Cheer의 writerKeyHash는 축제 종료 후 7일 내 삭제 대상
- Club, Place, TimetableSlot, Notice, FestivalPhoto는 다음 축제 재사용을 위해 보존 가능(사진은 총동연 보존 정책에 따름)

## 부록 A. 매칭 알고리즘

```
score(a, b) =
    1   × |공통 태그|
  + 2   × (같은 공연 선택)
  + 1   × (나이대 동일)  또는  0.5 × (나이대 인접: 19-21↔22-24↔25-27↔28+)
  제외: 차단/신고 관계(어느 방향이든), 이전 회차에 매칭된 쌍
  ※ 가중치·N·누적 기준은 AppSetting으로 관리
```

1. 회차 풀 구성: 해당 회차의 신청 전체(신규 + 자동 생성된 이월 신청 + 재참여 신청). 취소·신고 누적 제재 대상은 제외. 보고 싶은 공연이 회차 발표 이후 시작 조건(FR-MT-05)을 만족하지 않으면 점수 계산에서 무시
2. 남/여 분리, 제외 규칙 적용
3. 1차 배정(1:1): 점수 높은 쌍부터 그리디. 다수 측 우선순위 = 이전 회차 미매칭자 > 신규
4. 2차 배정(1:N): 다수 측 잔여자를 소수 측 전원에게 라운드 로빈으로 자동 추가 배정, 1인당 최대 N=3. 각 추가 배정도 점수 높은 순
5. 잔여자는 미매칭 → 발표 시점에 다음 회차 신청 자동 생성(마지막 회차면 종료)
6. 운영자 확인 후 발표 시각에 동시 공개

예시: 여 30 / 남 50 → 1차 30쌍, 잔여 남 20 → 여성 30명에게 라운드 로빈 +1 → 여성 20명은 2명, 10명은 1명과 매칭, **전원 매칭**. 여 30 / 남 130이면 2차에서 여성 1인당 최대 3명(총 90)까지 배정되고 남 10명은 미매칭.

## 부록 B. 인증 흐름 요약

```
방문 ─▶ 로그인 없이 읽기: 홈(카운트다운)·타임테이블·라인업·지도·축제 사진·공지·분실물·응원 메시지
   │      로그인 없이 쓰기: 응원 메시지 작성 (익명 키 쿠키 + 콘텐츠 필터 + 속도 제한)
   │
   └─ 쓰기 시도(신청 / 분실물 작성 / 신고) ─▶ 미로그인이면 로그인 게이트(카카오 / 구글)
            └─▶ OAuth(서버 코드 교환) ─▶ (provider, providerUserId)로 User 조회/생성
                     └─▶ JWT{uid} HttpOnly 쿠키 발급 ─▶ 원래 화면 복귀(입력값 복원)
                              └─▶ 쓰기 완료 → 자동 생성 닉네임으로 표시, 서버에는 uid 기록
로그아웃 ─▶ 쿠키 삭제 (데이터 유지)
```
